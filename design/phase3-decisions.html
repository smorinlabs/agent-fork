agent-fork Phase 3 — design decisions (D2–D14)

Thirteen pick-one decisions. Each opens with context and a ★ recommendation — recommendations are pre-selected, so change any you disagree with, add notes, then Export → MD (or click “Here are my answers”) and paste the result back into chat.

sec-01

What should a bare fork carry over by default?

What this is: agent-fork duplicates your current work into a new git worktree (a second working directory sharing the same repository) so a second agent session can continue it in parallel. "Exact-copy" also transfers your uncommitted work — files staged for commit, edited-but-unstaged files, and brand-new untracked files — so the copy looks exactly like where you left off. "Clean-from-HEAD" starts the copy at your latest commit with none of that.

Why you're being asked: This default defines what the one-word gesture means, and every flag and config key downstream is phrased relative to it (decision D3).

Continues in-flight workDistinct from plain git worktree add
Exact-copyYes — dirty state travelsYes — this is the tool's core value
Clean-from-HEADOnly committed workBarely — git does this natively

Prior art: agent-deck (the production tool this extracts from) makes its one-key quick-fork comprehensive-by-default, and its maintainers later reversed exactly one piece of it — gitignored-file copying — after it dragged in secrets and gigabyte caches. That reversal is baked into both options here: gitignored stays off unless explicitly requested.

★ Recommendsch-01-aExact-copy — the tool exists to continue in-flight work; a clean worktree at the parent's commit is what plain git worktree add already gives you.

Pick one — decision D3. This sets the defaults everything else builds on.

ch-01-aExact-copy: carry staged + unstaged + untracked (gitignored stays off)★ recComprehensive by default — the fork continues your in-flight work; tweak down with flags.
ch-01-bClean-from-HEAD: worktree at the parent's commit, no uncommitted stateMinimal by default — carrying state becomes an opt-in flag.
sec-02

How should the state choice appear in flags and config?

What this is: The words users type to change what a fork carries. agent-deck models it as two independent toggles — with_state (carry uncommitted work) and with_ignored (also carry gitignored files, which implies the first) — so the CLI flags would be --no-with-state and --with-ignored. The alternative is one named mode (--clean) treating exact-vs-clean as a single switch.

Why you're being asked: This fixes flag names, config keys, and help text — the part of the interface that cannot change compatibly later (decision D2).

★ Recommendsch-02-aThe agent-deck toggles — one vocabulary, a proven schema with tri-state semantics, trivial flag/env/config parity; a --clean alias can be added compatibly later.

Pick one — decision D2. Defines the flag vocabulary and config keys.

ch-02-aagent-deck toggles: --no-with-state / --with-ignored flags, with_state / with_ignored config keys★ recOne vocabulary, direct port of the proven schema; flag↔env↔config name parity is trivial.
ch-02-bA named mode: --clean flag, mode = "exact" | "clean" in configFewer flags on the happy path, but a second vocabulary for the same axis — and --with-ignored still exists.
ch-02-cToggles canonical plus --clean as a documented alias for --no-with-stateBoth vocabularies from day one.
sec-03

Where should the fork's worktree directory land?

What this is: The filesystem location of the fork's new working directory. For a repo at ~/c/myapp forked as fix-auth: sibling = ~/c/myapp-fix-auth; central = ~/.local/share/agent-fork/worktrees/myapp/fix-auth; subdirectory = ~/c/myapp/.worktrees/fix-auth. "Mirror the parent's pattern" means: when you fork from a directory that is itself a fork, place the new one the way that one was placed.

Why you're being asked: This is where users will physically find their forked code, and where cleanup will later delete directories (decision D5).

★ Recommendsch-03-aSibling with mirror-parent — agent-deck's default, matches hand-made worktree layouts, and keeps fork-of-fork placement consistent.

Pick one — decision D5. A worktree_location config override exists in every variant.

ch-03-aSibling dir <repo>-<branch-slug>; mirror the parent's pattern when the parent is itself a worktree★ recagent-deck's default plus the kickoff's mirror rule for already-forked parents.
ch-03-bSibling dir always — no mirroring heuristicSimplest predictable rule; nested forks may land somewhere surprising.
ch-03-cCentral forks dir under XDG data (~/.local/share/agent-fork/worktrees/<repo>/…)Keeps project parents clean, but hides working code far from the repo.
ch-03-dInside the repo: <repo>/.worktrees/<branch-slug>agent-deck's 'subdirectory' option; keeps everything under one root.
sec-04

Where does a fork's name come from?

What this is: The fork's single identity string. It becomes the branch name (behind the fork/ prefix), the worktree directory suffix, and — per sec-05 — the session's display name. Typed example: agent-fork fork fix-auth. Auto example: forking from branch feat-login on July 21 yields feat-login-0721, bumped to -2, -3 on collision.

Why you're being asked: agent-deck derives its name from the session's title — agent-fork has no title to slug, so the fallback scheme has to come from somewhere (decision D4).

★ Recommendsch-04-aOptional positional with auto-derived fallback — preserves the zero-argument flow while letting a human name the fork when it matters.

Pick one — decision D4. The name seeds the branch slug, worktree suffix, and session name.

ch-04-aOptional positional (agent-fork fork fix-auth); auto-derived from branch + date when omitted★ recAuto form: <parent-branch-slug>-<mmdd>, collisions suffixed -2, -3 (agent-deck's scheme).
ch-04-bRequired positional — a name must always be givenAlways explicit, but breaks the zero-argument one-word flow.
ch-04-cAlways auto-generated — no name argument acceptedZero decisions at fork time, zero control.
sec-05

What display name does the forked session get?

What this is: Coding agents show a display name for each saved session (Claude Code's --name appears in its prompt box, resume picker, and terminal title). This decides what the forked session is called there.

Why you're being asked: The launch command bakes the name in (-n '…'), so it must be derivable at fork time from information the CLI actually has (decision D6). The environment exposes the parent session's id, not its human display name — templates built on the parent's name would need extra discovery machinery.

★ Recommendsch-05-aUse the fork name — one identity across branch, worktree, and session; no discovery machinery needed.

Pick one — decision D6.

ch-05-aThe fork name itself — one identity across branch, worktree, and session★ rec"fix-auth-2" is the branch suffix, the directory suffix, and the session you pick in /resume.
ch-05-bA parent-derived template like {parent}-fork-{n}Richer lineage, but the parent's display name is not reliably discoverable (env exposes only its id).
ch-05-cNo name — let the agent use its defaultLoses findability in session pickers.
sec-06

What should happen when a native session fork is impossible?

What this is: Both target agents can natively fork a session (full conversation copy) — but only on recent versions: Claude Code needs ≥2.0.73 for pinned-id forks, Codex needs ≥0.81.0 for codex fork, and Codex also needs its session file flushed to disk first. The tool checks all of this before emitting a command ("preflight"). This decides what happens when the check fails.

Why you're being asked: The Phase 1 research pass on handoff conventions returned nothing verified, so this is a design-from-first-principles call (decision D14). A "handoff file" = a generated HANDOFF.md in the new worktree carrying the parent session id, anchor commit, branch, a status snapshot, and a task-notes slot the agent skill fills in — the fresh session reads it and continues informed, though without the parent's conversation memory.

★ Recommendsch-06-aThe two-rung ladder — never emit a command known to fail; degrade to a fresh named session seeded with the handoff file. Leave the vendor-unstable session-file-copy trick out of v1.

Pick one — decision D14. Applies when preflight finds an old CLI, a missing Codex rollout, or an unrelated directory.

ch-06-aDegradation ladder: native fork, else fresh NAMED session + generated HANDOFF.md seeded via the launch command★ recPreflight picks the rung before emitting; the handoff carries parent id, anchor commit, branch, status snapshot, and a task-notes slot the skill fills.
ch-06-bRefuse with a diagnosis — no fallback rung in v1Simplest and honest, but old-CLI users get nothing.
ch-06-cThe ladder plus a third rung: copy the Claude session file into the target project dirManipulates a format Anthropic declares internal and version-unstable; research verdict was last-resort-only.
sec-07

Should fork verification run by default?

What this is: After creating the fork, the tool can prove it worked: the new worktree sits at the right commit and branch, git registers it, the copy's git status output is byte-identical to the parent's (for exact-copy), and the parent was left untouched. A failed check rolls the fork back instead of handing it over.

Why you're being asked: agent-deck documents this exact contract but only enforces it in its test suite — at runtime it assumes success from exit codes. Enforcing it live is agent-fork's chance to be strictly safer at negligible cost (decision D8).

★ Recommendsch-07-aOn by default with --no-verify — milliseconds of git calls, and a paste-command tool should not hand over an unverified fork.

Pick one — decision D8.

ch-07-aOn by default; --no-verify to skip★ recA handful of git status/rev-parse calls — milliseconds — and a failed check rolls the fork back.
ch-07-bOff by default; --verify to enable (agent-deck parity)agent-deck verifies only in its test suite, never at runtime.
sec-08

Should the paste command land on the clipboard in v1?

What this is: The tool's final output is one shell command the user pastes into a fresh terminal. Clipboard assist puts that command on the clipboard so the paste is immediate. OSC52 is a terminal escape sequence that sets the clipboard from inside the terminal — it works even through SSH and tmux, where pbcopy/xclip shell-outs cannot reach your local clipboard.

Why you're being asked: The kickoff marked this a stretch goal; the question is whether it earns a v1 slot and whether it should ever happen without being asked for (decision D9).

★ Recommendsch-08-aShip it as an explicit --copy flag with OSC52 first — cheap, SSH/tmux-safe, and explicit beats a silent side effect.

Pick one — decision D9 (the kickoff's stretch goal).

ch-08-aYes — a --copy flag (config default off); OSC52 first, then pbcopy/xclip; failure is a notice, never an error★ recOSC52 writes the clipboard through SSH and tmux; shell-outs are the fallback.
ch-08-bDefer clipboard entirely to v1.1Keeps v1 lean; the command still prints on stdout.
ch-08-cCopy by default when on a TTY, with --no-copy to opt outOne less keystroke, but a silent clipboard write surprises people.
sec-09

Should v1 ship an agent-fork list command?

What this is: The tool keeps a small local registry recording each fork it creates (name, branch, worktree path, agent, parent session). That registry must exist anyway so cleanup knows what it owns. list would print it.

Why you're being asked: Scope control — every v1 command adds test and doc surface, and the command count sits at the small-CLI profile's boundary (decision D10).

★ Recommendsch-09-aYes — a thin read over data that exists anyway; without it, cleanup targeting is guesswork.

Pick one — decision D10.

ch-09-aYes — read the fork registry; show name, branch, worktree, agent, and whether the worktree still exists★ recThe registry exists anyway for cleanup ownership; list is a thin read.
ch-09-bDefer — git worktree list covers it for nowOne less command, but cleanup targeting goes blind.
sec-10

What may cleanup remove, and what stops it?

What this is: cleanup deletes a fork's worktree directory and (unless told to keep it) its branch — the tool's one destructive command. Two independent dials: which targets it may touch (only forks recorded in its own registry, or any git worktree), and which guard conditions block it (uncommitted changes, commits not pushed to any remote, or the target being the directory you are standing in).

Why you're being asked: Blast radius. Per the CLI standard, --force overrides guard conditions and --yes answers the consent prompt — this decision fixes what force may extend to (decision D12).

★ Recommendsch-10-aRegistry-scoped with --force as the deliberate escalation — safe by default on exactly what agent-fork made, with an operator path to clean anything.

Pick one — decision D12. Consent (--yes) is separate from guards in every variant.

ch-10-aRegistry-scoped: only forks agent-fork created; --force extends to any worktree AND overrides the dirty/unpushed guards★ recGuards: uncommitted changes; commits on no remote (no upstream counts as unpushed); target is your current directory.
ch-10-bAny worktree from the start, with the same guards everywhereMore useful as a general tool, more dangerous on worktrees it didn't make.
ch-10-cRegistry-only, permanently — --force never extends the target setSafest; orphaned or hand-made worktrees need manual git.
sec-11

What is the removal command called?

What this is: The org's CLI standard has a core verb set where removal is delete; other names need either an established-domain-verb justification or a recorded waiver. cleanup is the name the project kickoff used; it removes the worktree, optionally the branch, prunes git's bookkeeping, and updates the registry.

Why you're being asked: Command names are permanent interface (renames need deprecation cycles), and this one is currently the only waiver in the conformance note (decision D13).

★ Recommendsch-11-aKeep cleanup — the kickoff's name, broader-than-delete semantics, waiver already recorded.

Pick one — decision D13.

ch-11-acleanup — the kickoff name (stays the one waived SHOULD in CONFORMANCE.md)★ recDoes more than delete: worktree + branch + prune + registry update.
ch-11-bdelete — the CLI standard's core verb (drops the waiver)Standard-pure; slightly undersells the multi-step semantics.
ch-11-cprune — docker-styleUsually implies sweep-all-stale rather than remove-this-one; could later be cleanup --all instead.
sec-12

How much configuration should v1 expose?

What this is: Which keys a user can set in agent-fork_config.toml (project and user scopes; file locations and precedence are already fixed by the CLI standard). The trimmed schema carries exactly the toggles decided in the sections above; agent-deck's original [fork] block additionally has docker (sandbox choice), a worktree on/off toggle, and inherit_from_parent (mirror a live parent session's runtime state) — none of which mean anything in a standalone CLI whose fork is a worktree.

Why you're being asked: Config keys are interface: every key needs validation, docs, and a deprecation path if removed later (decision D7).

★ Recommendsch-12-aThe trimmed schema — every key mirrors a flag decided above; the three meaningless-here agent-deck keys stay dropped.

Pick one — decision D7. File locations and precedence are already fixed by the CLI standard; this is only about which keys exist.

ch-12-aTrimmed schema tracking today's answers: with_state, with_ignored, branch_prefix, worktree_location, verify, copy★ recEvery key mirrors a flag decided above; drops agent-deck's docker, worktree toggle, and inherit_from_parent.
ch-12-bMinimal: branch_prefix only — everything else is flagsLeanest possible; users re-type preferences per invocation.
ch-12-cFull agent-deck [fork] port including inherit_from_parentMaximum familiarity; carries keys with no meaning in a standalone CLI.
sec-13

Should per-agent extra-args passthrough ship in v1?

What this is: A config hook like [agents.claude] extra_args = ["--model", "opus"] that injects user-chosen arguments into the launch command agent-fork emits. agent-deck supports the equivalent for its managed sessions.

Why you're being asked: With it, v1's emitted commands are no longer fixed strings — every test and quoting guarantee gains a variable; without it, power users wait a release for model/flag control (decision D11).

★ Recommendsch-13-aDefer — v1 templates stay byte-for-byte testable; passthrough is additive later, designed against real requests.

Pick one — decision D11.

ch-13-aDefer to v1.1 — keep v1's launch templates fixed and testable★ recAdding [agents.claude] extra_args later is additive and non-breaking.
ch-13-bShip in v1: [agents.<name>] extra_args injected into emitted commandsPower users get --model etc. now; adds a quoting/injection surface to v1.
