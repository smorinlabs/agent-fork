# agent-fork — Version String Consolidation: Design Options

**Date:** 2026-08-18 · **Status:** draft, reviewed by Fable (one adversarial round, all findings dispositioned below), pending owner decision.
**Method:** Direct repo search across all file types (an earlier pass missed `.json`/`.sh` files), cross-checked against a real version bump that landed while this doc was being written (PR #47, `1.0.0` → `1.1.0`). Verified against live repo state, git history, and an empirical `uv lock` test. This doc proposes options only — no implementation until the owner picks one.

---

## 1. Problem

`agent-fork`'s own release version (currently `1.1.0`, source of truth `pyproject.toml:3`) is duplicated as a hardcoded literal string in **9 places across 7 files**. Bumping the version requires editing all of them by hand; nothing enforces that they agree.

| Category | Files | Count |
|---|---|---|
| Source of truth | `pyproject.toml:3` | 1 |
| Auto-regenerated by `uv lock` — confirmed by running it: bumping `pyproject.toml` and re-running `uv lock` correctly updated `uv.lock`'s version | `uv.lock:7` | 1 |
| Runtime-dynamic, reads `pyproject.toml`'s built metadata via `importlib.metadata.version("agent-fork")`, never manually edited | `src/agent_fork/__init__.py:5`, `src/agent_fork/cli.py:57` | 2 |
| **Hardcoded literals — the actual problem** | `src/agent_fork/codex_app_server.py:122`, `tests/cli/test_cli.py:43`, `scripts/check_clean_install.sh:12`, `.claude-plugin/plugin.json:3`, `.claude-plugin/marketplace.json:9` and `:16`, `.codex-plugin/plugin.json:3`, `README.md:147` and `:190` | **9** |

**Evidence this is a real, not theoretical, risk:** PR #47 bumped the version from `1.0.0` to `1.1.0`. Of the 9 hardcoded literal sites, it updated **2** (`tests/cli/test_cli.py`, `scripts/check_clean_install.sh`) and **missed 7, across 5 files** — including `README.md`, which the PR *did edit* (29 lines changed) without touching either of its two stale version mentions. The failure mode isn't "forgot to open the file" — it's "edited the file, still missed the version string in it."

Current stale state (still `1.0.0` after the merge): `src/agent_fork/codex_app_server.py:122`, `.claude-plugin/plugin.json:3`, `.claude-plugin/marketplace.json:9` and `:16`, `.codex-plugin/plugin.json:3`, `README.md:147` and `:190`.

**Why the 9 hardcoded sites split into three different problems, not one:**

- **A real bug in source code** (`codex_app_server.py:122`): this is a JSON-RPC handshake to the Codex app-server, sent by running Python code. It should follow the same pattern `__init__.py`/`cli.py` already use — `importlib.metadata.version("agent-fork")` — but doesn't, and never has.
- **Intentional tripwires** (`tests/cli/test_cli.py`, `scripts/check_clean_install.sh`): both run in CI (the `matrix-and-tests` and `conformance` jobs) and assert the *expected* version string as a smoke test that a release actually shipped the version it claims to. If they read the version dynamically instead of hardcoding it, they could never catch "we forgot to bump `pyproject.toml`" — a real failure mode a release process needs to catch. These are working as designed; the risk is that nothing *else* catches the sites they don't cover.
- **Independent-but-currently-coupled manifests** (`.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` ×2, `.codex-plugin/plugin.json`, `README.md` ×2): JSON/Markdown files with no Python runtime, so they can't call `importlib.metadata` even if we wanted them to. These aren't all the same kind of "version" either — `.claude-plugin/plugin.json:3` and `.codex-plugin/plugin.json:3` are the **plugin's** version; `.claude-plugin/marketplace.json:16` is the same plugin's version restated inside the marketplace listing; `.claude-plugin/marketplace.json:9` is the **marketplace listing's own** version (`metadata.version`), a third, conceptually distinct object. All four currently happen to match the PyPI package version, with nothing enforcing that.

## 2. A constraint the first draft of this doc missed: release-please is already planned

This repo's own backlog already commits to an answer for *how version bumps should work*, and it isn't written yet:

- `projects/P01-agent-fork-v1.md` — **P01-T20** (`[ ]`, not started): *"Release plumbing: release-please, PyPI + TestPyPI trusted publishing, Homebrew tap."*
- `REQUIREMENTS.md` **REQ-36**: *"Release automation per the org's release-please pattern."*
- `IMPLEMENTATION-PROMPT.md` Phase F: release plumbing via `repo-please-setup`, before the first real release is cut (**P01-T21**, also `[ ]`).

release-please supports bumping arbitrary extra files via its `extra-files` config (the exact updater type — JSON-path vs. regex-in-text — needs to be worked out per file when T20 is implemented). That config exists to do exactly the job a hand-rolled bump script would do. Two consequences:

1. A hand-rolled `scripts/bump_version.sh` written now is likely **throwaway work** once T20 lands, and could actively conflict with release-please's own version-bump commits/PRs if both mechanisms try to own the same files later.
2. A **drift-detection test**, by contrast, is mechanism-agnostic — it doesn't care whether the version was bumped by hand, by a script, or by release-please. It survives T20 unchanged, and would double as a correctness check *on* release-please's `extra-files` config once that's built (if `extra-files` is misconfigured for one of these files, the drift test catches it immediately instead of at the next accidental audit).

This is why the option set below includes a variant that adds the enforcement (test) now without adding bump automation (script) that a near-future, already-committed project will replace.

## 3. Options

**Every option below includes, as an explicit first deliverable: repair the 7 currently-stale hardcoded sites to `1.1.0`.** None of the mechanisms proposed prevent CI from immediately failing (Option C/D) or the repo from staying visibly wrong (Option A/B) unless the existing drift is fixed as part of adopting whichever option is chosen — this was missing from the first draft.

### Option A — Fix the one real bug, document the rest

Fix `codex_app_server.py` to use `importlib.metadata.version("agent-fork")`, matching `__init__.py`/`cli.py`. Repair the other 7 stale literals by hand to `1.1.0`. Add an explicit "bump these 8 files" checklist to a new `RELEASING.md` (none exists today — verified; there is currently no release checklist anywhere in the repo, so this is a net-new safeguard, not a previously-tried one).

- **Effort:** trivial — one code fix, one round of manual literal repairs, one new checklist doc.
- **What it fixes:** the one place where hardcoding was clearly unintentional (source code, not test or manifest); the current visible drift.
- **What it doesn't fix:** the manifests and docs remain manual on every future bump, protected only by a document nobody is currently required to consult. PR #47's miss happened without any checklist in place, so this option is genuinely untested against the failure mode it's meant to prevent — it might work, but there's no evidence yet either way.
- **Ongoing risk:** highest of the four options. Every future bump repeats the same manual-edit surface that just failed.

### Option B — Automated bump script

Do everything in Option A (minus the checklist, which the script replaces), plus add `scripts/bump_version.sh <new-version>` that rewrites every hardcoded site **idempotently** — each site is rewritten by matching its own pattern (`"version": "..."` at a specific JSON path; `agent-fork X.Y.Z` in test/script/README) and replacing it with the target version, regardless of what version it currently holds. This is important: the 7 sites are not all on the same version right now (some say `1.0.0`, some `1.1.0`), so a naive "replace old string with new string" pass would not converge from today's actual state — idempotent-per-site rewrites do, and this is also how the script performs the drift repair from §3's opening paragraph. The script prints a diff before the author commits.

- **Effort:** moderate — one new shell script (~40-60 lines), one-time.
- **What it fixes:** removes the manual-edit failure mode for anyone who runs the script.
- **What it doesn't fix:** someone can still hand-edit `pyproject.toml` and skip the script, silently reproducing the current bug — no safety net. Per §2, this script is also likely superseded by release-please's `extra-files` mechanism once P01-T20 is implemented, meaning some of this effort is throwaway.
- **Ongoing risk:** low, contingent on the script being used every time. Additional risk not present in A: maintaining a script that may need to be deleted/replaced when T20 lands.

### Option C — Bump script plus a drift-detection test

Everything in Option B, plus a test (extend `tests/test_package.py`, which already reads other repo files by path and runs in the default `just all`/CI suite) that reads `pyproject.toml`'s version and asserts the 9 known hardcoded sites match it, failing CI on any mismatch.

This needs one explicit design choice the first draft didn't name: **enumerated-list vs. repo-wide scan.**
- *Enumerated list* (check exactly these 9 known file:line sites): precise, no false positives, but — as `codex_app_server.py` itself proves, since nobody knew to protect it either — blind to a *10th* hardcoded site introduced later. Doesn't fully close the gap this whole doc is about.
- *Repo-wide scan* (grep for `agent-fork \d+\.\d+\.\d+`-shaped or bare-semver-near-"version" patterns anywhere, flag anything that doesn't match `pyproject.toml`): future-proof against new hardcoded sites, but needs an **allowlist** for legitimate historical version mentions that should *not* track current — e.g. `docs/testing/CLI-STANDARDS-AUDIT.md`, `docs/superpowers/plans/2026-08-16-p02-a1-content-verification.md`, and `projects/P01-agent-fork-v1.md` itself, which intentionally preserves the old `v0.1.0` target language (see the earlier turn's finding on this — that's deliberate history, not drift). Building and maintaining that allowlist is real, ongoing design work, not a one-line addition.

This doc does not pick between them — it's an owner call (see §4/§5).

- **Effort:** moderate-plus — B's script, plus the test (enumerated: small and fast to build; scan: bigger upfront, needs allowlist curation).
- **What it fixes:** closes the exact gap PR #47 fell into — the enumerated version would have failed PR #47's CI outright; the scan version would also have caught it *and* would catch the next `codex_app_server.py`-style miss in new code.
- **What it doesn't fix:** carries Option B's release-please redundancy risk (§2) on top.
- **Ongoing risk:** lowest for the *known* sites (enumerated) or lowest overall (scan, at the cost of allowlist upkeep).

### Option D — Drift test now, defer bump automation to the planned release-please work

Fix `codex_app_server.py` (as in A), repair the 7 stale sites now, add the drift-detection test from Option C (enumerated or scan — same open choice), but **skip the bump script**. Version bumps stay manual until P01-T20 lands; the drift test is what makes manual bumps safe in the interim, because it fails CI the moment a bump is incomplete — which is a strictly better outcome than what PR #47 experienced (silent merge, discovered only by this out-of-band audit).

- **Effort:** the smallest of the automation-bearing options — no script to write or later retire.
- **What it fixes:** the exact PR #47 failure mode, immediately, permanently, without building anything that P01-T20 is likely to replace.
- **What it doesn't fix:** manual bumps are still manual until T20 ships — but they're now a "fix the 9 things CI just told you about" task instead of a "hope you remembered all 9" task.
- **Ongoing risk:** low. The only cost relative to Option C is slightly more manual toil per bump between now and T20 — bounded by however soon T20 is actually worked (currently `[ ]`, unscheduled).

## 4. Recommendation

**Option D**, with the enumerated-list drift test to start (not the repo-wide scan). Reasoning:

- The demonstrated failure (PR #47) is an *enforcement* gap, not an *automation* gap — nothing caught the miss, and a drift test is precisely the thing that catches it. The bump script in B/C is a convenience for the person doing the bump, which is a smaller problem than "nobody, including CI, noticed the bump was incomplete."
- Building `scripts/bump_version.sh` now, ahead of a release-please migration this repo has already committed to (P01-T20/REQ-36), risks throwaway work and a future collision between two systems trying to own the same file edits. Deferring it costs little — bumps stay manual, but now they're checked.
- Start with the enumerated list, not the repo-wide scan, because the scan's allowlist-of-legitimate-historical-mentions is real, non-trivial design work (§3, Option C) that shouldn't block shipping the enforcement this doc is actually about. The enumerated list already closes the concrete, demonstrated gap (PR #47's 7 misses); the scan is a legitimate future hardening step once P01-T20 is closer and the manifest/version landscape has settled.

If the owner expects P01-T20 to be far off (i.e., several more releases will happen under the current manual process before release-please lands), Option C becomes more attractive despite the redundancy risk, since it removes hand-editing sooner rather than later. That's a judgment call about T20's timeline that only the owner can make — see §5.

`codex_app_server.py`'s fix and the repair of the 7 currently-stale sites are common to every option and should happen regardless of which is chosen.

## 5. Open questions for the owner

1. **T20 timeline:** how soon is release-please work (P01-T20) actually expected? This is the deciding factor between Option D (defer bump automation) and Option C (build it now anyway).
2. **Scope of "the version" for `.claude-plugin/marketplace.json`:** does `metadata.version` (the marketplace listing's own version, line 9) need to track the PyPI package version at all, or is it a genuinely independent number (e.g., bumped when the marketplace *listing* changes, not when the package does)? This doc assumed 1:1 tracking for all four plugin/marketplace fields based on current behavior (they've always matched), but `metadata.version` in particular may be a different kind of thing from the plugin's own version (`plugins[].version`, line 16) and deserves an explicit ruling before it's added to any drift test.
3. **`README.md:147`** ("PyPI and Homebrew releases land with v1.0.0…") is forward-looking prose about a release that hasn't happened yet (PyPI still holds the `0.0.0.dev0` placeholder per REQ-36) and is likely to be deleted, not updated, once P01-T21 actually ships. Should it be excluded from tracking now and handled as a one-time deletion at release time instead of being kept version-accurate in the meantime?
4. **Enumerated vs. scan** (Option C/D's shared sub-choice, §3): confirmed above as starting with enumerated — flag if that reasoning doesn't match the owner's risk tolerance.
